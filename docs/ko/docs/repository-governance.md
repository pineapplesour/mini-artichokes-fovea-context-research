# 저장소 거버넌스

최종 업데이트 날짜: 2026년 5월 15일(KST)

이 문서는 유니버설 아티초크에 대한 저장소 권한 모델, 검토 작업 흐름 및 기록 보호 요구 사항을 정의합니다.

## 대상 권한 모델

의도된 운영 모델은 다음과 같습니다.

| 역할 | GitHub 기능 | `main` 권한 |
|---|---|---|
| 소유자 | Repository 관리, 최종 릴리즈 승인, 긴급 복구 | `main`을 승인하고 병합할 수 있습니다. 의도적으로 브랜치 규칙을 변경할 수 있습니다. |
| 팀장 | 팀 브랜치 및 PR에 대한 검토 및 병합 결정을 담당합니다. 팀 PR을 승인할 수 있습니다. `main`을 다시 쓰거나 삭제하면 안 됩니다. |
| 팀원 | 브랜치를 생성하고, 자체 브랜치를 커밋하고, PR을 엽니다 | `main`에 직접 푸시할 수 없습니다. 보호된 공유 분기를 강제로 푸시하거나 삭제할 수 없습니다. |
| 리뷰어 | 리뷰 및 의견 | 별도로 부여되지 않는 한 병합 또는 기록 다시 쓰기 권한이 없습니다. |

중요한 차이점은 **쓰기 액세스만으로는 거버넌스가 충분하지 않습니다**라는 점입니다. 팀 구성원은 브랜치에 커밋할 수 있어야 하지만, 보호 브랜치 규칙은 `main`의 직접 쓰기, 강제 푸시, 삭제를 방지해야 합니다.

## 현재 GitHub 시행 상태

2026-05-15 KST에 확인됨:

```text
repo: pineapplesour/universal-artichoke
visibility: PRIVATE
default branch: main
viewer permission: ADMIN
```

GitHub API에서 반환된 현재 협력자에게는 `admin` 또는 `write` 저장소 역할이 있습니다. 일반 `write` 공동 작업자는 브랜치를 생성하고 커밋을 푸시할 수 있지만, 이 개인 저장소에서는 현재 브랜치 보호 및 규칙 세트 API가 다음을 반환합니다.

```text
HTTP 403: Upgrade to GitHub Pro or make this repository public to enable this feature.
```

따라서 대상 모델은 **문서화되었지만 아직 호스팅된 저장소에서 완전히 시행할 수는 없습니다**. 브랜치 보호 또는 ruleset을 사용할 수 있을 때까지 `write` 공동 작업자는 보호되지 않은 브랜치에 직접 푸시할 수 있습니다. 이는 완전한 통제가 아닌 운영상의 위험입니다.

## 필수 호스팅 설정

광범위한 팀 개발을 시작하기 전에 다음 중 하나를 구현해야 합니다.

1. private 브랜치 보호 및 저장소 ruleset을 사용할 수 있는 GitHub plan 또는 조직으로 저장소를 업그레이드/이동합니다.
2. 리포지토리를 조직으로 이동하고 `team-leads`, `engine-team`, `frontend-team`, `db-team` GitHub 팀을 만듭니다.
3. 코드/데이터 정책에서 허용하는 경우에만 리포지토리를 공개합니다.

그런 다음 `main`에 대한 규칙 세트를 구성합니다.

- 직접 업데이트를 소유자/팀 리더 우회 행위자에게만 제한합니다.
- 강제 push를 차단합니다.
- branch 삭제를 차단합니다.
- 병합 전에 풀 요청이 필요합니다.
- 코드 소유자의 검토가 필요합니다.
- 새로운 커밋이 푸시되면 오래된 승인을 해제합니다.
- 대화 해결이 필요합니다.
- `repo-contracts` 상태 확인이 필요합니다.
- 해당 영역을 터치할 경우 추가 엔진/프론트엔드/DB 상태 확인이 필요합니다.

동일한 강제 푸시 및 삭제 제한을 사용하여 `release/*` 및 `prod/*`와 같은 공유 릴리스 분기를 구성합니다.

## 브랜치 권한

허용되는 작업 분기 접두사:

```text
team1/engine/<short-topic>
team2/ui-fix/<product-or-bug>
team3/design/<product>
db/<short-topic>
docs/<short-topic>
hotfix/<short-topic>
```

팀 구성원은 자신의 작업 브랜치에 커밋을 푸시할 수 있습니다. 팀 리더는 팀의 브랜치를 관리하고, 검토를 조정하고, 검토가 시작되기 전에 재작성을 요청할 수 있습니다. 브랜치가 검토되면 팀 리더가 명시적으로 리베이스나 정리를 요청하지 않는 한 기록이 보존되어야 합니다.

소유자 외에는 누구도 파괴적인 저장소 작업을 수행해서는 안 됩니다. 팀 리더는 팀 브랜치를 관리할 수 있지만 `main`을 삭제하거나, `main`의 이름을 바꾸거나, `main`을 강제 푸시하거나, `main` 기록을 다시 작성해서는 안 됩니다.

일반 개발은 반드시 작업 브랜치에서 진행합니다. `main` 병합은 브랜치에서 기능과 검증이 완전히 통과하고, 소유자가 명시적으로 승인한 뒤에만 수행합니다.

## 코드오너 정책

현재 `.github/CODEOWNERS` 파일은 개인 저장소이기 때문에 `@pineapplesour`를 사용합니다. 이는 프로젝트가 실제 GitHub 팀이 있는 조직으로 이전될 때까지 신뢰할 수 있는 유일한 소유자 핸들입니다.

조직 팀이 존재하는 경우 소유자 핸들을 팀 핸들로 바꿉니다.

```text
@team-leads
@engine-team
@frontend-team
@db-team
```

CODEOWNERS는 검토 요청만 전달합니다. 분기 보호에 코드 소유자 검토가 필요한 경우에만 병합을 차단합니다.

## 기록 삭제 금지 정책

정상적인 개발에는 다음이 금지됩니다.

- `main`, `release/*` 또는 `prod/*`에 강제 push합니다.
- `main`, `release/*` 또는 `prod/*`를 삭제합니다.
- 팀장의 승인 없이 검토가 시작된 후 공유된 검토 기록을 다시 작성합니다.
- PR 토론에서 검토 증거, 검증 아티팩트 또는 사건 컨텍스트를 제거합니다.
- `git filter-repo`, 강제 리베이스 또는 공유 기록에 대한 강제 푸시를 일상적인 정리 도구로 사용합니다.

비밀 파일이나 법적으로 민감한 파일이 커밋된 경우 정상적인 작업을 중단하고 사건으로 처리해야 합니다. 사고 대응을 위한 기록 재작성은 소유자가 통제하며 문서화해야 합니다.

## 풀 리퀘스트 요구 사항

모든 PR에는 다음이 포함되어야 합니다.

- 목적 및 영향을 받는 계층
- 접촉된 계약 파일;
- 검증 명령 및 결과
- UI/API/엔진 동작이 변경된 경우 실제 사용자 경로 아티팩트;
- 롤백 메모;
- 팀 간 영향 노트.

`main`에 대한 직접 푸시는 소유자가 제어하는 저장소 설정 또는 긴급 수리 중에만 허용됩니다. 일반 기능, 문서, DB, 디자인 작업은 브랜치에서 완료하고 소유자 승인을 받은 뒤 병합해야 합니다. 커밋 메시지나 작업 로그에는 동일한 검증 표준을 계속 포함해야 합니다.
