# 팀 협업 워크플로우

최종 업데이트 날짜: 2026년 5월 15일(KST)

Universal Artichoke는 공유 계약을 위반하지 않고 DB, 엔진, 프런트엔드, 운영 작업이 병렬적으로 진행될 수 있도록 구성됩니다.

## 작동 원리

- 팀은 브랜치에서 작업하고 풀 요청을 제출합니다.
- 팀장은 범위를 조정하고, 구현 품질을 검토하고, 계약 준수를 확인합니다.
- 소유자는 변경사항이 `main`에 들어가기 전에 최종 승인을 제공합니다.
- 계약 변경 사항은 구현과 동일한 PR에 버전이 지정되고 문서화됩니다.
- 검증 증거는 선택적인 후속 조치가 아닌 결과물의 일부입니다.
- `main` 직접 푸시는 기본 작업 흐름이 아닙니다. 모든 일반 작업은 브랜치에서 완전히 작동하는 상태로 만든 뒤, 명시적인 소유자 승인 후에만 `main`에 병합합니다.

## 수요일 리뷰 케이던스

팀은 의미 있는 움직임이 있을 때마다 진행 상황을 보고할 수 있습니다. 정식 심사 체크포인트는 매주 수요일입니다.

각 팀 리더는 다음을 제공해야 합니다.

- 완료된 변경 사항.
- 달성한 목표.
- 실행한 명령 및 검증 결과.
- UI/API/엔진 동작이 변경되었을 때 실제 동작을 증명하는 아티팩트.
- 남은 방해 요소와 다음 단계 제안.

팀 리더는 조정 및 확인을 담당합니다. 소유자는 계약 위반, 오래된 아티팩트 또는 테스트되지 않은 사용자 경로를 발견한 첫 번째 사람이 되어서는 안 됩니다.

## 브랜치 작업 흐름

권장 브랜치 이름:

```text
team1/engine/<short-topic>
team2/ui-fix/<product-or-bug>
team3/design/<product>
db/<short-topic>
docs/<short-topic>
hotfix/<short-topic>
```

팀 구성원은 자신의 작업 브랜치에 커밋할 수 있습니다. 팀 리더는 팀 브랜치를 관리하고 검토 전에 정리를 요청할 수 있습니다. 검토가 시작되면 팀 리더가 명시적으로 요청하지 않는 한 강제 push를 피해야 합니다.

`main`은 작업 브랜치가 아닙니다. 실험, 설계 탐색, 벤치마크 시험 또는 임시 데이터 게시를 위해 `main`을 사용하지 않아야 합니다.

`main` 병합 대상 브랜치는 다음 조건을 충족해야 합니다.

- 해당 브랜치 자체에서 제품이 완전히 작동합니다.
- 관련 contract/test/verifier가 통과합니다.
- UI/API/엔진/native 동작이 바뀌면 실제 사용자 경로 아티팩트가 있습니다.
- 소유자가 승인하기 전에는 `main`에 병합하지 않습니다.

| 운영/리드 | CI, 브랜치 정책, 배포 스크립트, 출시 프로세스 | 검토 및 롤백 보장 |

## 주간 교육 파일

팀 지침은 다음 위치에 게시됩니다.

```text
tasks/team-instructions/week-YYYY-MM-DD/
```

각 팀 파일에는 다음이 명시되어야 합니다.

- 범위
- 팀이 자유롭게 편집할 수 있는 파일이나 폴더
- 팀 간 검토가 필요한 파일
- 필수 테스트 및 검증자
- 변경되어서는 안 되는 계약
- 예상되는 핸드오프 아티팩트.

기여자는 편집하기 전에 관련 주간 파일과 `README.md`, `STRUCTURE_REQUIREMENTS.md` 및 로컬 레이어 요구 사항을 읽어야 합니다.

## 검토 체크리스트

모든 PR 또는 직접 소유자 제어 설정 커밋은 다음 사항에 응답해야 합니다.

- 이 변경이 어떤 계약에 닿습니까?
- 어떤 파일이 변경되었나요?
- 어떤 명령을 실행했고 결과는 무엇입니까?
- 동작이 변경되었을 때 실제 사용자 경로를 테스트했습니까?
- 오래된 실험 파일이 남아 있나요?
- 변경하려면 DB 릴리스, native shell 동기화 또는 배포 업데이트가 필요합니까?
- 롤백 경로는 무엇입니까?

## 정리 규칙

매니페스트, 경로, 문서, 테스트 또는 릴리스 인벤토리에서 참조되지 않는 실험 파일은 병합하기 전에 제거하거나 명시적 아카이브로 이동해야 합니다.
