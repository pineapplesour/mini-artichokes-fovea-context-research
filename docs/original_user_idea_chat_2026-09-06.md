3. 가장 중요한 부분: “텍스트→PNG”가 아니라 “정보→적절한 화면”으로 컴파일

단순한 구현은 이런 식입니다.

터미널 로그 3만 줄 → 작은 글씨의 PNG 수십 장

제 설계에서는 두 종류의 시각 표현을 구분하겠습니다.

A. 원문 보존형 이미지

문서나 코드의 실제 내용을 읽어야 할 때 사용합니다.

코드를 구문 강조해서 렌더링하거나, 문서를 적정 밀도로 배치하는 방식입니다. 이것은 기존 optical compression과 가깝습니다.

B. 관계·상태를 보여주는 기억판

전체 원문보다 무엇이 무엇과 연결되는지, 무엇이 바뀌었는지가 중요할 때 사용합니다.

예를 들어 다음은 가상의 디버깅 기록입니다.

로그 원본:
실행 1: 테스트 37개 실패
실행 2: 설정 변경 후 9개 실패
실행 3: 캐시 초기화 후 2개 실패
나머지 수천 줄: 반복되는 스택트레이스

이것을 단순히 작은 글씨로 넣지 않고 다음과 같은 화면으로 컴파일합니다.

[실행 A]             [실행 B]             [실행 C]
37개 실패  ───────→   9개 실패  ───────→   2개 실패
          설정 변경             캐시 초기화

남은 실패:
[P17] 만료 토큰 처리
[P18] 동시 갱신 처리

확인된 사실:
P17은 A·B·C에서 계속 실패
P18은 B부터 발생

미확정 가설:
동시성 문제일 가능성 — 아직 검증 안 됨

이 화면의 숫자와 연결은 파서와 실제 실행 기록에서 생성합니다. 모델이 “그럴듯한 원인관계”를 그림에 넣게 하지 않습니다. 가설은 관측 사실과 별도로 표시합니다.

그리고 각 패널에는 원문 연결이 있습니다.

P17 → 실행 C의 로그 1482~1516행
P18 → 실행 C의 로그 1517~1560행

왜 두 표현을 구분하나?

원문 보존형 이미지는 토큰화 방식을 바꾸는 압축입니다.

관계형 기억판은 선별·집계·구조화까지 포함하는 변환입니다.

둘을 섞어 놓고 “이미지 덕분에 10배 압축됐다”고 하면 안 됩니다. 상당 부분은 중복 제거와 정보 선별의 효과일 수 있습니다.

그래서 같은 내용을 텍스트 표나 구조화된 텍스트로 표현한 버전도 함께 만들고, 이미지가 실제로 더 유리한 경우에만 이미지 버전을 선택하겠습니다.

콘텐츠마다 다른 컴파일러를 사용

코드는 함수·클래스·호출관계 단위로, 로그는 실행·오류 유형 단위로, 대화는 요구사항·결정·반박·미해결 문제 단위로 분해합니다. 스크린샷은 원본 화면과 관심 영역을 연결합니다.

특히 취소된 결정과 최신 결정을 구분해야 합니다.

이전 결정: Redis를 제거한다.
후속 결정: Redis를 유지하되 TTL만 변경한다.

이 두 문장을 같은 무게로 기억판에 남기는 대신, 이전 결정에는 superseded 상태를 붙입니다. 최신 상태는 짧은 텍스트로도 제공합니다.

오래됐다는 이유만으로 중요도가 낮아지는 것은 아닙니다. 최초 요구사항, 금지사항, 아직 해결되지 않은 실패 원인은 계속 유지합니다.

5. 표현 선택: 이미지가 이기는 항목에만 이미지 사용

각 기억 단위에 다음 후보를 만들겠습니다.

EXACT_TEXT       원문 텍스트
BRIEF_TEXT       구조화된 짧은 텍스트
LITERAL_IMAGE    원문을 렌더링한 이미지
STRUCTURE_IMAGE  관계·변화를 보여주는 이미지
REFERENCE_ONLY   주소와 색인만 유지

선택 기준은 단순히 이미지 토큰 < 텍스트 토큰이 아닙니다.

> 지금 넣는 비용 + 이후 반복해서 읽는 비용 + 필요할 때 원문을 다시 가져오는 비용 + 캐시를 깨뜨리는 비용 + 잘못 읽었을 때의 위험



을 합쳐서 판단합니다.

기존 구현에서 실제로 개선할 지점

imgctx의 gate.py는 텍스트 길이를 chars_per_token으로 나누고, 이미지 면적을 pixels_per_token으로 나누는 방식으로 비용을 근사합니다. 제 설계에서는 이 부분을 모델별 계측기로 교체하겠습니다. 

현재 OpenAI 문서에서도 이미지 비용은 모델, 이미지 크기, detail, 리사이즈 규칙에 따라 달라집니다. 예를 들어 문서상 GPT-5.4의 detail: high에서 1024×1024 이미지는 약 1,229 입력 토큰으로 계산됩니다. 따라서 “PNG 한 장은 항상 1천 토큰” 같은 상수로 판단하면 안 됩니다. 

프로필에는 다음을 저장하겠습니다.

모델·버전
이미지 토큰 계산 규칙
서버의 리사이즈 규칙
렌더링 설정별 읽기 성능
캐시 읽기·쓰기 가격
이미지 입력 제한
최근 실제 usage와 예측 오차

읽기 성능도 계측

같은 모델에 대해 렌더링 설정을 바꾸며 다음을 검사합니다.

본문 요지 파악, 특정 오류 위치 찾기, 비슷한 이름의 함수 구분, 부정문·예외 조건 읽기, 숫자·기호 읽기입니다.

단, 모델이 “잘 읽었다”고 말하는 자기평가를 신뢰도 점수로 쓰지는 않겠습니다. 정답이 있는 검증 데이터에서 측정한 성능을 사용합니다.

특히 해시·UUID·정확한 명령 인자처럼 오류 비용이 높은 정보는 이미지 판독에 맡기지 않습니다. 필요 시 원문 조회를 강제합니다.

6. 캐시 설계: 이미지가 같아도 캐시가 유지되는 것은 아님

여기가 실제 제품에서 가장 중요한 부분입니다.

로컬 이미지 캐시와 모델 제공자의 프롬프트 캐시는 다릅니다.

로컬 이미지 캐시:
같은 원문을 다시 PNG로 그리지 않음

프롬프트 캐시:
모델 입력의 동일한 앞부분에 대해 이전 계산을 재사용

Anthropic은 캐시 구간까지의 텍스트와 이미지를 포함한 프롬프트가 정확히 일치해야 한다고 명시합니다. 따라서 PNG가 같아도 그 앞의 내용이나 순서가 바뀌면 해당 구간의 캐시 재사용이 깨질 수 있습니다. 

제가 사용할 정책: 고정된 기억 구간 + 뒤에 추가되는 변경분

한 작업 구간을 epoch라고 부르겠습니다.

Epoch 시작:
[고정 지시]
[선택된 기억판·색인]
[현재 작업]

같은 Epoch 안:
기존 내용은 유지
새 결과와 변경사항을 뒤에 추가

여기서 중요한 것은 매 턴마다 “최근 6턴”을 다시 계산해서 나머지를 이미지로 바꾸지 않는 것입니다. 그러면 과거 프롬프트가 계속 바뀔 수 있습니다.

대신 두 시점에 표현을 결정합니다.

새로운 큰 도구 결과가 처음 들어오는 순간에 이미지·텍스트 중 하나를 선택합니다. 이미 오랫동안 캐시된 과거 내용을 재구성하는 것은 작업 전환이나 명시적인 컨텍스트 재편 시점으로 모읍니다.

새 사실이 생겨도 기존 이미지에 내용을 덧그리지 않습니다.

기존 P17 이미지는 고정

새 텍스트 변경분:
"P17의 실패는 run-108에서 해결됨.
 최신 근거는 P29."

원본 기록과 이미지는 유지하고, 최신 상태만 추가합니다.

왜 이렇게 해야 하나: 간단한 손익 계산

다음은 특정 모델 가격이 아니라 가격 비율을 가정한 예시입니다.

일반 입력 가격 = 1
캐시 읽기 가격 = 0.1
캐시 쓰기 가격 = 1.25

기존: 이미 캐시된 텍스트 10,000토큰
변환: 새 이미지 4,000토큰

기존 텍스트를 한 번 더 읽는 비용은 1,000입니다. 새 이미지의 첫 캐시 쓰기는 5,000입니다.

그 뒤에는 이미지 읽기가 400으로 싸지지만, 다른 비용을 무시해도 총 8번 사용할 때부터 이미지 전환이 유리해집니다.

8회 사용:
텍스트 유지 = 8 × 1,000 = 8,000
이미지 전환 = 5,000 + 7 × 400 = 7,800

렌더링 비용, 원문 재조회, 뒤쪽 캐시 무효화가 있으면 손익분기점은 더 늦어집니다.

따라서 곧 끝날 작업의 오래된 캐시를 굳이 이미지로 바꾸는 것은 손해일 수 있습니다.

또 앞선 답변의 “OpenAI는 캐시 쓰기 할증이 없다”는 일반화는 수정해야 합니다. 현재 공식 문서는 GPT-5.6 이후 모델에 캐시 쓰기 요금을 명시합니다. 설계에서는 제공자 이름이 아니라 실제 모델별 정책을 사용해야 합니다.

7. 한 단계 더 나가는 부분: “필요하면 확대”가 아니라 “행동에 필요한 근거를 미리 준비”

모델이 이미지마다 확대 도구를 호출하면, 토큰은 줄어도 왕복 호출이 늘어날 수 있습니다.

그래서 현재 작업의 예상 다음 행동에 맞춰 원문을 미리 선택하겠습니다.

예를 들어 사용자가 “로그인 동시성 버그를 고쳐라”라고 요청했다면:

넓은 맥락:
인증 모듈 관계도
이전 실패·해결 시도
관련 테스트의 변화

원문으로 미리 준비:
현재 수정 후보 함수
실패 테스트 본문
가장 최근의 관련 스택트레이스

이렇게 하면 모델은 넓은 범위를 이미지로 보면서, 수정에 필요한 부분은 추가 호출 없이 정확한 텍스트로 읽을 수 있습니다.

단, 이 예측을 메인 모델의 비싼 호출로 매번 수행하지는 않겠습니다. 초기 버전에서는 파일명·심볼·최근 편집 대상·실패 테스트와 의존관계로 후보를 정합니다. 시각 문서에 대해서만 ColPali 계열 검색을 추가 후보 경로로 사용합니다.

동일한 정보를 다른 해상도로 중복 제공하는 것도 제한

개요 이미지 전체
+ 읽기용 이미지 전체
+ 원문 전체

를 동시에 넣으면 압축 의미가 없습니다.

기본적으로 넓은 범위의 개요 + 좁은 범위의 정확한 근거만 제공합니다. 원문을 가져온 구간은 이후 컨텍스트 재편 시 해당 이미지 상세 내용을 대체할 수 있도록 합니다.

이 구조의 목표는:

> 모든 내용을 흐릿하게 기억하게 하는 것이 아니라, 넓은 관계는 유지하면서 다음 행동에 필요한 부분만 선명하게 만드는 것



입니다.

8. Codex·Claude Code에 붙인다면 이렇게 구현

처음부터 전체 요청을 가로채는 거대한 프록시로 시작하지 않겠습니다.

1차 구현: 원본 저장소 + 읽기용 MCP

먼저 memory.lookup과 memory.open을 제공하는 로컬 MCP 서버를 만듭니다. MCP는 이미지 형태의 도구 결과를 지원하고, Codex도 MCP를 통해 외부 도구와 컨텍스트를 연결할 수 있습니다. 

이 단계에서는 긴 문서·로그를 처음부터 이 서버를 통해 읽게 해서 전체 원문이 컨텍스트에 들어오는 것을 예방합니다.

이미 CLI 내부에 쌓여 있는 과거 이력을 MCP만으로 전부 교체할 수 있다고 가정하지는 않습니다.

2차 구현: 도구 결과가 들어오는 지점에서 변환

Claude Code의 현재 공식 문서는 PostToolUse의 updatedToolOutput으로 모델에 전달되는 결과를 바꿀 수 있다고 설명합니다. 다만 내장 도구의 출력 스키마를 맞춰야 합니다. additionalContext로 요약을 덧붙이는 것과 원래 결과를 교체하는 것은 다릅니다. 

따라서 긴 출력은 원본 저장소에 보존한 뒤, 해당 도구가 허용하는 형태로 작은 결과와 조회 주소를 제공합니다. 이미지 자체는 지원되는 이미지 콘텐츠 경로로 전달합니다.

Base64 문자열을 일반 텍스트 결과에 넣고 이미지라고 취급하는 구현은 하지 않습니다.

3차 구현: 전체 컨텍스트 재편

전체 과거 이력을 교체하려면 하네스 수준의 통합이나 요청 변환 계층이 필요합니다.

이 단계에서는 도구 호출과 결과의 연결, 메시지 역할, 추론·압축 관련 불투명 항목을 보존해야 합니다. 실제 imgctx/codex.py도 도구 결과를 짧은 표식으로 바꾸고 별도의 이미지 메시지를 추가하는 방식 등, API 형태에 맞춘 별도 처리를 합니다. 이 코드는 참고하되 역할과 출처를 어떻게 유지할지는 다시 설계하겠습니다. 

특히 외부 로그나 문서 속 내용이 이미지화되면서 사용자 지시나 시스템 지시처럼 승격되지 않도록 하겠습니다.

구현 모듈

fovea_ctx/
  ingest/          이벤트 수집·원본 저장
  parse/           코드·로그·대화 분해
  provenance/      출처·버전·상태 추적
  render/          원문형·관계형 이미지 생성
  retrieve/        텍스트·심볼·시각 검색
  budget/          토큰·캐시·재조회 비용 계산
  evidence/        원문 핸들·수정 전 검증
  adapters/        MCP·Claude hooks·Codex 통합
  eval/            정확도·비용·회귀 테스트

초기 저장소는 로컬 데이터베이스와 콘텐츠 해시 기반 파일 저장소로 충분하게 설계하겠습니다. 시각 검색용 모델은 선택 기능으로 두겠습니다.

또한 이미지 렌더링 전에 비밀정보를 처리하고, 외부 콘텐츠는 실행되지 않는 리터럴로 렌더링합니다. 컨텍스트 퇴거는 입력에서 제외한다는 의미이지, 원본 파일이나 기록을 삭제한다는 의미가 아닙니다.

9. 얼마나 줄어들 수 있나: 반드시 “전체 작업”으로 계산

예를 들어 한 시점에 80k 입력을 사용하던 작업을 다음 예산으로 구성한다고 가정하겠습니다.

고정 지시·도구 정의                10k
현재 작업·최근 원문                 8k
색인·최신 상태·정확한 식별자          2k
선택된 이미지                       8k
미리 가져온 원문 근거                4k
────────────────────────────────────
총 입력 예산                       32k

이 시점만 보면 60% 감소입니다.

하지만 이 숫자는 다음을 모두 합친 결과입니다.

원본 외부 저장, 중복 제거, 관련 내용 선택, 이미지 표현, 필요한 원문의 선택적 복귀.

즉 “이미지의 압축률 2.5배”라고 부르면 안 됩니다.

더 중요한 문제는 추가 호출입니다.

기존:
80k 입력으로 한 번 호출

새 구조:
32k 입력으로 판단
+ 원문 확인 뒤 36k 입력으로 추가 호출
= 총 68k

이 경우 총입력 절감은 **15%**입니다. 캐시 때문에 실제 청구액은 또 다르게 나올 수 있습니다.

OCR-Memory 논문도 이런 자원 간 교환을 보고합니다. 해당 실험에서 추론 모델에 주입되는 텍스트는 감소했지만 저장 공간과 검색 지연은 증가했습니다. 따라서 “메인 모델에 들어간 텍스트만 줄었다”와 “시스템 전체가 저렴해졌다”는 별도로 측정해야 합니다. 

제가 최종적으로 최적화할 지표는 이것입니다.

\[
\text{성공한 작업당 비용}
=
\frac{
\text{모든 모델 호출}
+\text{검색·렌더링 비용}
+\text{재시도 비용}
}{
\text{성공한 작업 수}
}
\]

입력 토큰 수는 이 목표를 위한 중간 지표입니다.

가장 중요한 비교 상대는 전체 원문이 아닙니다.

똑같이 원문 저장소와 검색을 사용하되, 이미지만 쓰지 않는 시스템입니다.

그 상대를 못 이기면 이 설계는 괜찮은 메모리 시스템일 수는 있어도, 이미지 기반 기술의 우월성을 보여준 것은 아닙니다.

비교군

비교군	확인하려는 것

초기 도입 판정 기준

다음은 연구 목표로 설정하겠습니다.

추가로 정확한 문자열 오류, 잘못된 버전 사용, 불필요한 원문 재조회, 캐시 적중률, 작업 완료 지연을 별도 측정합니다. 토큰은 줄었지만 수정 실패와 재시도가 늘면 탈락입니다.

11. 더 연구적으로 밀어붙인다면: “압축률”보다 “어디를 선명하게 볼지”를 학습

학습이 가능한 오픈 모델까지 사용한다면, 다음 단계에서는 시각적 주의 배분 정책을 학습시키겠습니다.

입력은 현재 질문, 기억판, 작업 상태, 남은 예산입니다. 출력은 다음처럼 제한합니다.

P17은 개요만 유지
P18은 읽기용 이미지가 필요
P22는 원문 40줄이 필요
P31은 현재 작업과 무관

학습 목표는 작은 이미지를 만드는 것이 아닙니다.

> 정답을 내는 데 필요한 근거를 빠뜨리지 않으면서, 총 읽기 비용을 최소화하는 것



입니다.

AgentOCR는 압축률 선택을 학습하고, LensVLM은 필요한 구간의 확장을 학습합니다. 제안하는 확장은 여기에 출처 정확성, 최신 버전, 전체 호출 비용, 캐시 교체 비용까지 포함한 선택 정책입니다. 

다만 이것은 오픈 모델의 검색기·선택기를 학습하는 경로입니다. Codex나 Claude의 내부 벡터를 직접 수정하거나 임의의 latent를 주입하는 것으로 설명하지는 않겠습니다.

FOVEA-CTX:

그 선택을 언제 바꿔야 전체 작업이 가장 저렴하고 정확한가?

이미지는 모든 기억을 담는 최종 저장 형식이 아니라, 많은 근거를 적은 입력으로 탐색하고 연결하는 인터페이스로 쓰겠습니다.

그리고 혁신성을 검증할 지점은 “PNG를 썼다”가 아니라, 동일한 검색·요약·캐시를 갖춘 텍스트 시스템보다 더 적은 비용으로, 더 정확한 근거를 확보하고, 실제 작업을 더 잘 끝내는가입니다.

내가 설계한다면 **“텍스트를 이미지로 압축하는 프록시”가 아니라, “이미지로 전체를 탐색하고 원문으로 정확하게 행동하는 메모리 시스템”**을 만들겠다.

가칭 FoveaContext. 핵심은 다음이다.

> 많은 정보를 작은 글씨로 욱여넣는 것이 아니라, 무엇을 기억하고 어디를 다시 읽어야 하는지를 시각적으로 표현한다. 정확성이 필요한 순간에는 해당 원문의 최신 버전을 강제로 가져온다.



여기에 캐시를 고려한 갱신 방식과 작업별 표현 선택기를 결합한다. Codex·Claude Code에 적용하는 비학습형 버전부터 만들고, 효과가 확인된 부분만 학습형으로 확장하는 설계다.

아래의 구조와 수치는 설계 제안·예시·검증 목표이며, 구현해서 성능을 측정한 결과는 아니다.

2. 전체 구조: 원본 저장소와 모델의 작업 기억을 분리한다

먼저 원본을 보관하는 공간과 모델에게 보여주는 공간을 완전히 나눈다.

파일·명령 결과·대화·스크린샷
             │
             ▼
    원본 이벤트 저장소
    원문 / 버전 / 출처 / 권한
             │
             ▼
      구조 분석 및 분할
    함수·문단·오류·표·사건
             │
             ▼
        표현 선택기
    ┌────────┼────────┬─────────┐
    ▼        ▼        ▼         ▼
 원문 text  구조화 text  시각 지도   참조 ID만
    └────────┴────────┴─────────┘
             │
             ▼
      현재 모델 컨텍스트
             │
       필요한 영역 선택
             │
             ▼
      원문 재조회 + 버전 확인
             │
             ▼
       편집·실행·최종 답변

원본 저장소에는 원문을 남기되, 모델 컨텍스트에는 현재 작업에 필요한 표현만 올린다. 컨텍스트에서 내려보내는 것은 파일이나 원본 데이터를 삭제하는 것과 다르다. 이 설계의 기본 보관 정책은 원본 자동 삭제가 아니다.

모든 기억에는 주소와 출처가 붙는다

내부 저장 형식은 대략 다음과 같다. 이것 전체를 모델에게 보내는 것이 아니라, 서버가 관리하는 메타데이터다.

{
  "id": "event-184",
  "kind": "tool_result",
  "source": {
    "tool_call_id": "call-37",
    "workspace": "project-A",
    "snapshot": "snapshot-52"
  },
  "trust": "untrusted_observation",
  "original_blob": "sha256:...",
  "regions": [
    {
      "id": "region-07",
      "byte_range": [8120, 11040],
      "view": "code",
      "visual_location": {
        "page": "page-12",
        "box": [0.1, 0.2, 0.9, 0.5]
      }
    }
  ]
}

중요한 것은 이미지 좌표 자체보다 다음 연결이다.

> 이미지 영역 → 원문 범위 → 해당 원문의 버전 → 그것을 만든 도구 호출



모델이 “오른쪽 아래 부분”을 골라도, 실제로 읽을 바이트 범위는 모델이 추측하지 않고 서버가 결정한다.

3. 첫 번째 핵심: 모든 이미지를 ‘읽는 용도’로 만들지 않는다

보통의 optical compression은 이렇게 접근한다.

긴 텍스트 → 작은 글씨의 이미지 → 모델이 읽기

나는 이미지에 세 가지 다른 역할을 부여하겠다.

A. 탐색용 지도: 내용을 전부 읽기 위한 이미지가 아니다

예를 들어 코드베이스라면 파일 본문을 빽빽하게 찍기보다 다음을 보여준다.

어떤 모듈이 어떤 모듈을 사용하는가.

어떤 테스트가 어느 함수와 연결되는가.

최근 수정한 부분과 실패한 부분이 어디서 겹치는가.


로그라면 원문 1만 줄 대신 오류 종류 × 시간 × 실행 단계의 행렬을 만들 수 있다. 같은 오류가 반복되는 구간, 새로운 오류가 나타나는 시점, 수정 이후 사라진 오류를 배치로 표현한다.

대화 기록이라면 요청 → 가설 → 시도 → 결과 → 아직 해결되지 않은 문제의 흐름을 만든다.

이것은 단순히 텍스트를 사진으로 바꾸는 것이 아니라 작업의 구조를 이미지로 컴파일하는 것이다.

단, 이런 변환은 원문 전체를 보존하는 압축이 아니다. 일부 정보를 선택해 보여주는 것이므로 빠진 정보는 반드시 원본 저장소에서 검색 가능해야 한다.

B. 읽기용 페이지: 필요할 때 실제 내용을 읽는다

함수 본문, 문서 단락, 오류 스택처럼 시각적으로 읽을 가치가 있는 내용은 비교적 선명한 페이지로 렌더링한다.

CodeOCR의 구문 강조·레이아웃 처리나 PixelPrompt의 내용별 렌더링 설정을 참고할 부분이다. 다만 특정 글꼴 크기가 모든 모델·언어에서 최적이라고 가정하지 않는다. 

C. 실행용 원문: 이미지를 사용하지 않는다

코드 수정, 정확한 숫자 인용, 경로·해시·정규식 사용처럼 문자 하나가 중요한 작업에는 원문을 가져온다.

따라서 같은 기억이 다음처럼 세 단계로 존재한다.

표현	모델이 해도 되는 일	해서는 안 되는 일

탐색용 지도	관련 영역 찾기, 관계 파악, 조사 순서 결정	작은 글자를 추측해서 정확한 값이라고 단정
읽기용 이미지	내용 이해, 가설 형성, 추가 조회 판단	원문 확인 없이 중요한 식별자·수정 내용을 확정
검증된 원문	정확한 인용, 편집 준비, 값 비교	버전이 바뀌었는데 그대로 실행


이 구분을 이미지 옆의 짧은 텍스트 메타데이터로 알린다.

혁신 포인트 후보는 압축률이 아니라, 기억마다 ‘이 표현으로 어디까지 판단해도 되는가’를 명시하는 것이다.

시각적 문법도 일관되게 만든다

페이지마다 배치를 무작위로 바꾸지 않는다. 예를 들어 테스트 분석 페이지에서는 행을 테스트 그룹, 열을 실행 순서로 고정한다. 코드 관계 페이지에서는 모듈별 구역을 고정한다.

다만 고정된 배치가 모델 성능을 높인다는 것은 여기서 검증할 가설이다. 인간에게 익숙하다고 모델에게도 유리하다고 가정하지 않는다.

또한 관계도는 가능하면 파서·실행 로그에서 생성한다. 정적 분석으로 확인한 호출 관계와 모델이 추정한 원인 관계를 같은 종류의 화살표로 표시하지 않는다. 관찰과 가설을 시각적으로도 구분한다.


---

4. 두 번째 핵심: 이미지 기억에서 곧바로 행동하지 못하게 한다

내가 가장 강하게 넣을 장치는 편집 전 원문 조회 증표다.

모델이 이미지에서 코드를 보고 다음처럼 판단했다고 하자.

> “인증 갱신 로직의 분기 조건을 수정해야 한다.”



바로 수정하도록 하지 않고 먼저 다음 도구를 호출하게 한다. 아래는 새로 제안하는 내부 프로토콜 예시다.

{
  "tool": "context.open",
  "references": ["page-12:region-07"],
  "representation": "source",
  "purpose": "edit"
}

서버는 다음을 돌려준다.

원문 코드
정확한 파일 경로
현재 파일 버전
대상 범위
read_ticket

이후 편집 요청에는 해당 증표가 필요하다.

{
  "tool": "workspace.apply_edit",
  "read_ticket": "read-92",
  "patch": "..."
}

서버는 수정 직전에 현재 파일이 조회 당시 버전과 같은지 확인한다. 달라졌으면 재조회를 요구한다.

이 장치가 해결하는 문제

이미지에 남은 코드는 과거 버전일 수 있다. 또한 모델이 user_id를 users_id로 잘못 읽었을 수도 있다.

이 구조에서는 이미지를 잘못 읽더라도 수정 직전에 실제 원문을 볼 기회가 생기며, 다른 도구나 사람이 파일을 변경한 경우도 버전 검사로 잡는다.

하지만 이 검사가 보장하는 것은 원문·버전의 일관성이다. 수정의 논리적 정당성이나 테스트 통과까지 보장하지는 않는다.

강제하려면 실행 계층을 통제해야 한다

여기서 중요한 구현상의 조건이 있다.

모델에게 “반드시 원문을 읽고 수정해”라고 지시하는 것만으로는 강제 장치가 아니다. 일반 셸로 파일을 덮어쓸 수 있으면 우회할 수 있다.

따라서 완전한 버전에서는 편집 도구와 파일 쓰기 경로를 통제해야 한다. MCP만 추가한 가벼운 버전에서는 이를 권고 수준의 흐름으로 제공하고, 하네스에 통합한 버전에서만 강제 보장을 주장한다.

시스템 지시, 아직 유효한 사용자 제약, 승인 정책, 도구 스키마는 계속 정확한 텍스트로 유지한다. 외부 문서나 로그에서 나온 문장은 이미지가 됐다고 상위 지시로 승격하지 않는다.


---

5. 세 번째 핵심: 매 턴 이미지를 다시 만들지 않는 ‘캐시 구간’

여기서는 앞선 대화보다 더 엄밀하게 볼 필요가 있다.

같은 PNG를 재사용하는 것과 모델의 prompt cache가 적중하는 것은 다르다. 캐시는 요청의 재사용 가능한 앞부분과 연결되고, 현재 OpenAI 문서는 모델·캐시 방식에 따라 공유 prefix에 적절한 breakpoint가 없으면 재사용이 안 될 수 있다는 점도 설명한다. Anthropic 역시 prefix와 캐시 설정을 기준으로 동작한다. 

따라서 이미지 파일만 content hash로 고정해서는 부족하다.

일정 구간 동안 메모리 배치를 고정한다

하나의 작업 구간을 epoch라고 부르겠다.

같은 epoch 안의 요청들

[보호된 지시·도구 정의]
[고정된 기억 페이지와 인덱스]
[이후 추가된 관찰·변경 사항]
[현재 질문·최근 도구 결과]

고정된 기억 페이지는 가능한 한 동일한 내용과 순서를 유지한다. 현재 관심 영역이 바뀌었다고 옛 이미지에 강조 표시를 다시 그리지 않는다.

대신 뒤쪽에 짧게 붙인다.

현재 조사 대상: page-12:region-07
page-08의 상태는 event-191에 의해 갱신됨.

모델이 새 영역을 열면 새 도구 결과로 추가한다.

오래된 내용은 덮어쓰지 않고 새 버전을 추가한다

기존 페이지:
인증 테스트 실패, snapshot-52

새 변경 기록:
snapshot-53에서 수정
관련 테스트 통과

매번 전체 지도를 다시 그리지 않고 변경 기록을 추가한다. 다만 과거 상태와 현재 상태가 혼동되지 않도록 현재 버전을 가리키는 짧은 인덱스를 둔다.

변경 기록이 너무 많아지거나 작업 단계가 끝났을 때 다음 epoch를 만든다. 이때 필요한 기억만 다시 선택하고, 새 prefix의 캐시 형성 비용을 지불한다.

새 epoch에서는 입력량이 줄지만 캐시 재사용이 감소할 수 있다. 둘 중 무엇이 이득인지 계산해야 한다. OpenAI 문서도 compaction 이후에는 토큰 감소와 캐시 감소를 함께 비교하도록 설명한다. 

프로토콜 구조는 별도로 보호한다

실제로 요청을 재구성할 때는 도구 호출과 결과의 연결, 아직 완료되지 않은 호출, 공급자가 요구하는 서명·불투명 상태를 건드리지 않는다.

고정 기억 블록이라는 이유로 과거 도구 출력을 임의의 시스템 메시지에 집어넣는 방식도 사용하지 않는다. 공급자별 어댑터가 유효한 메시지 구조 안에서 표현을 교체해야 한다.

6. 네 번째 핵심: ‘이미지로 만들지 말지’를 자동 결정한다

이미지화를 기본값으로 두지 않는다.

각 정보 조각에 대해 다음 네 가지 후보를 비교한다.

① 원문 텍스트
② 구조화된 짧은 텍스트
③ 시각 지도 또는 읽기용 이미지
④ 짧은 참조만 유지하고 필요할 때 조회

선택 기준은 단순한 입력 토큰 수가 아니다.

\[
\text{총비용}
=
\text{입력비용}
+\text{출력비용}
+\text{렌더링·검색비용}
+\text{추가조회비용}
+\text{재시도비용}
\]

여기에 응답 시간과 오류 위험을 제약으로 둔다.

예를 들어:

작은 JSON에서 값 두 개만 필요한 작업이라면 서버가 해당 값을 정확하게 추출해 텍스트로 주는 것이 후보가 된다. 굳이 JSON 전체를 이미지로 만들 필요가 없다.

여러 차례의 테스트 결과를 비교하는 작업이라면 실패 양상을 표시하는 행렬 이미지가 후보가 된다.

현재 수정하는 함수라면 원문 텍스트를 선택한다.

관련성이 낮은 오래된 로그라면 이미지조차 보내지 않고 참조만 보관한다.

캐시까지 포함하면 판단이 달라진다

가령 다음을 가정하자.

기존 텍스트: 10,000 tokens, 이미 캐시되어 있음
이미지 표현:  2,500 tokens, 아직 캐시되지 않음

Anthropic 문서에 일반적으로 제시된 배율인 캐시 읽기 0.1×, 5분 캐시 쓰기 1.25×를 적용하는 예다. 모델별 예외가 있으므로 실제 구현에서는 해당 모델의 요율을 사용해야 한다. 

시점	텍스트 유지	이미지로 교체

첫 요청	1,000 비용 단위	3,125 비용 단위
이후 캐시가 적중하는 요청마다	1,000	250


이 단순화된 예에서는 첫 요청과 이후 세 번의 재사용, 총 네 번부터 이미지 쪽 누적 비용이 낮아진다.

그러나 실제로는 다른 prefix의 캐시 손실, 메타데이터, 원문 재조회 비용까지 추가된다. 따라서 작업이 곧 끝날 예정이면 기존 캐시 텍스트를 유지하는 편이 나을 수 있다.

토큰 계산도 공급자별로 분리한다

OpenAI는 모델·detail에 따라 이미지의 patch/tile 처리와 리사이즈 규칙을 구분한다. Claude의 현재 문서도 시각 토큰 계산과 해상도 조건을 따로 명시한다. 하나의 면적 공식으로 모든 모델을 처리하면 안 된다. 

구현에서는 다음 값을 기록한다.

model + version
image dimensions + detail
예상 입력 토큰
실제 API usage
캐시 읽기·쓰기
원문 재조회 횟수
전체 작업 비용

PixelPrompt의 렌더러는 참고할 만하지만, 확인한 compare()는 텍스트 토큰을 len(text) // 4로 추정한다. 그 결과를 실제 API 절감률로 쓰지 않는 이유다.

7. 실제 코딩 작업에서는 이렇게 움직인다

가상의 작업을 하나 보자.

> “로그인 실패 버그를 고쳐라. 여러 번 테스트했고 이전 시도도 많다.”



처음에는 전체 원문 대신 조사 지도를 보여준다

모델에게 다음을 제공한다.

정확한 텍스트:
현재 사용자 요구
보호해야 하는 제약
최근 수정 내용

시각 지도:
인증 관련 모듈 관계
테스트 실패의 시간적 변화
이미 시도했지만 실패한 수정들
아직 검증하지 않은 가설

여기서 중요한 기억은 “오래전에 무슨 말을 했는가”만이 아니다.

무엇을 시도했고, 어떤 증거 때문에 그 가설을 버렸는가도 남긴다. 같은 잘못된 수정을 반복하는 비용을 줄이기 위한 설계다.

관련 영역을 한꺼번에 연다

모델이 갱신 토큰 처리와 실패한 테스트가 관련 있다고 판단하면 두 영역을 묶어서 요청한다.

{
  "tool": "context.open",
  "references": [
    "auth-map:refresh-handler",
    "test-map:refresh-failure"
  ],
  "representation": "source",
  "purpose": "edit"
}

단건 확대를 반복하기보다 가능한 범위에서 배치 조회한다. 다만 관련 코드가 확실하게 검색된다면 지도 탐색을 생략하고 바로 원문을 가져오는 빠른 경로도 둔다.

수정 후에는 전체 기억을 다시 만들지 않는다

편집 증표를 확인하고 수정한 뒤 테스트를 실행한다. 새 결과는 새 이벤트로 추가한다.

event-205:
갱신 로직 수정
대상 테스트 통과
다른 인증 테스트 미실행

“테스트 통과”를 “문제 완전 해결”로 확대하지 않고, 검증 범위도 함께 저장한다.

작업 단계가 끝나면 새 epoch에서 오래된 상세 페이지를 내려보내고 결정 과정과 필요한 원문 참조를 남긴다. 원본은 계속 저장소에 있다.

8. Codex·Claude Code에 붙이는 현실적인 구현 순서

1단계: MCP로 새 입력부터 줄인다

처음에는 다음 세 도구만 노출하는 형태가 적절하다.

context.search   관련 기억·파일·영역 검색
context.overview 선택된 자료의 시각적 개요
context.open     해당 영역의 이미지 또는 정확한 원문

Codex와 Claude Code는 MCP 연결을 지원하고, MCP 도구 결과에는 텍스트와 이미지 콘텐츠를 포함할 수 있다. 

여기서는 큰 파일이나 로그를 처음 읽을 때부터 원문 전체 대신 적절한 표현을 반환한다.

단, MCP 서버를 추가했다고 기존 대화 전체나 모든 내장 도구 출력을 마음대로 교체할 수 있는 것은 아니다. 이 단계의 범위는 새 도구를 통해 들어오는 컨텍스트를 관리하는 것이다.

2단계: 요청 조립 계층에 통합한다

과거 컨텍스트까지 적극적으로 재구성하려면 하네스 또는 요청 변환 계층과 통합해야 한다.

Codex는 custom model provider 설정을 제공한다. 다만 연결 경로를 설정할 수 있다는 것과 모든 요청 형태·상태 관리가 호환된다는 것은 별개다. 실제 사용 경로에 대한 적합성 테스트가 필요하다. 

Claude Code 쪽도 처음부터 전체 세션을 변환하기보다 새롭고 큰 도구 결과부터 시작하겠다. 기존 캐시를 크게 흔드는 전체 history 변환은 나중에 비교한다.

구독 인증 정보를 임의로 꺼내 우회하는 구조에 의존하지 않고, 정식으로 지원되는 연결과 승인된 인증 경로를 사용한다. 또한 API 비용 감소가 구독형 제품의 사용 한도 증가를 뜻한다고 가정하지 않는다.

내부 모듈은 이렇게 나눈다

foveacontext/
  store/        원본, 스냅샷, 출처, 버전
  compiler/     코드·로그·문서 분석, 시각 표현 생성
  planner/      표현 선택, 비용 추정, epoch 관리
  retrieval/    심볼·텍스트·시각 검색
  tools/        조회 API, 편집 전 원문 증표
  adapters/     MCP, 공급자별 메시지 변환
  evaluation/   작업 재현, 비용 계측, 비교 실험

초기 검색은 심볼·텍스트 검색부터 시작한다. ColPali 계열의 시각 검색은 도표·스크린샷처럼 시각 정보가 중요한 자료에서 추가한다. 이미 원문 텍스트를 가진 코드에까지 시각 검색 비용을 무조건 지불하지 않는다.

9. 효과를 증명하려면 ‘이미지 없는 버전’을 반드시 이겨야 한다

이 설계에서 가장 중요한 실험은 다음이다.

> 동일한 원문 저장소·동일한 검색기·동일한 편집 검증을 쓰면서, 시각 지도만 텍스트 인덱스로 바꾼 버전과 비교한다.



그 비교가 없으면 절감 효과가 이미지 때문인지, 단순히 불필요한 기록을 제거하고 검색을 잘해서인지 구분할 수 없다.

비교군은 다음 정도면 된다.

비교군	확인할 질문

원문 + 기존 캐시·컨텍스트 관리	기본 에이전트보다 실제로 나은가?
Aider식 텍스트 지도 + 원문 검색	시각적 개요가 텍스트 개요보다 유리한가?
텍스트 요약·압축 + 원문 검색	이미지 대신 텍스트를 줄이는 것으로 충분하지 않은가?
단순 텍스트→이미지 변환	복잡한 관리 구조가 추가 비용만 만드는 것은 아닌가?
FoveaContext 전체	정확도·비용·시간을 함께 개선하는가?


텍스트 압축 비교군에는 LLMLingua 계열도 포함할 수 있다. 비시각적 대안을 약하게 만들어 놓고 이미지가 낫다고 주장해서는 안 된다. 

측정 단위는 ‘성공한 작업 하나’다

입력 토큰 감소율만 보지 않는다.

전체 작업 성공률, 실패를 포함한 총비용, 완료 시간, 최대 컨텍스트 크기, 원문 재조회 횟수, 잘못된 식별자 사용, 오래된 버전으로 행동한 횟수를 함께 기록한다.

특히 이미지 때문에 추론이나 재조회가 늘면 입력 절감이 상쇄될 수 있다. LensVLM도 확대된 내용까지 반영한 effective compression을 평가하고, 압축이 강해질수록 원문 확장 의존도가 커지는 현상을 보고한다. 

반드시 넣을 실패 테스트

긴 정상 문서만으로 평가하지 않는다. 비슷하게 생긴 식별자, 정확한 숫자, 한국어·영문 혼합, 길게 이어지는 문자열, 드문 오류 한 줄, 오래된 파일 버전, 상충하는 지시가 들어 있는 도구 출력 등을 포함한다.

그리고 고정된 배치를 무작위로 바꾼 버전, 캐시 정책을 뺀 버전, 시각 지도를 뺀 버전으로 각각 비교한다.

내가 설정할 초기 연구 목표는 다음 정도다.

강한 텍스트 기반 비교군 대비
작업 성공률은 사전에 정한 허용 범위 안에서 유지
성공 작업당 총비용은 20% 이상 감소
심각한 오래된 버전 편집은 검증 계층에서 차단

이 숫자는 기대 성능이 아니라 채택 여부를 결정할 목표다. 작은 파일럿으로 오류를 찾을 수는 있지만, 성공률 차이가 1%포인트 이내라는 식의 주장을 하려면 그에 맞는 충분한 표본과 신뢰구간이 필요하다.

10. 더 혁신적으로 가려면: 압축률이 아니라 ‘읽을 곳 선택’을 학습한다

비학습형 버전에서 시각 지도의 이득이 확인되면, 다음에는 어떤 내용을 얼마나 선명하게 보여줄지를 학습시키겠다.

학습 목표를 “이미지에서 원문을 얼마나 잘 복원했는가”로만 두지 않는다.

대신 다음에 보상을 준다.

작업을 해결했는가?
필요한 원문 영역을 적은 횟수로 찾았는가?
불필요한 영역을 얼마나 덜 열었는가?
최신 근거를 사용했는가?
전체 비용과 시간이 얼마나 들었는가?

VIST는 고정된 vision encoder와 학습 가능한 resampler로 압축된 시각 토큰을 만드는 구조를 제안한다. 이런 접근은 자체 모델을 학습하는 단계에서 참고할 만하다. 

다만 Codex·Claude API를 그대로 쓰는 버전에서는 내부 latent를 직접 주입하는 것으로 설계하지 않는다. 먼저 외부 선택기와 렌더러를 학습하는 범위로 제한한다.

그리고 자체 모델까지 바꿀 수 있다면, 이미지 경로뿐 아니라 직접적인 텍스트 압축·잠재 메모리도 같은 조건에서 비교해야 한다. 이미지가 반드시 최종 형태라고 정해 놓을 이유가 없다. 앞서 언급한 비판 연구가 바로 그런 비교의 필요성을 보여준다.

최종적으로 내가 노리는 차별점

이미지를 기억의 원본으로 사용하지 않고, 원본에 접근하는 주소 공간으로 사용한다.

그 주소 공간에 다음을 함께 넣는다.

무엇과 무엇이 연결되는지, 어떤 시도가 실패했는지, 현재 유효한 버전은 무엇인지, 정확한 행동 전에 어디를 다시 읽어야 하는지.

그래서 이 기술의 핵심 질문은 “10만 토큰을 이미지 몇 장에 넣을 수 있나?”가 아니다.

> “작업 전체를 덜 잊으면서, 정확한 원문은 필요한 순간에만 읽도록 만들 수 있나?”



내가 먼저 만들 버전은 시각적 작업 지도 + 원문 영역 주소 + 편집 전 버전 검증 + 캐시를 고려한 갱신 정책이다. 이 조합이 동일한 텍스트 기반 시스템보다 비용 대비 성능을 높이는지 검증하겠다.

이미지가 이기는 자료에서는 이미지를 쓰고, 텍스트가 이기는 자료에서는 텍스트를 쓰게 만드는 것까지가 이 설계의 일부다.35s 동안 처리함

그냥 2천만~3천만 토큰을 작은 글씨로 이미지에 박아 넣는 방식은 거의 확실히 망가집니다. 문제는 파일 크기가 아니라 모델이 실제로 보는 시각 해상도와 visual-token 수입니다.

현재 GPT-5.6 Sol 기준 original 이미지는 32×32px patch로 처리되고, 이미지 하나가 30,000 patches를 넘으면 요청 자체가 거절됩니다. 즉 정사각형이라면 대략 5.5K×5.5K 수준이 실질적인 한계입니다. 이미지 토큰도 컨텍스트를 그대로 소비하며 GPT-5.6 Sol의 전체 context window는 1.05M입니다. 

한 장에 2천만 토큰을 넣는다고 생각해보면

영문에서 아주 거칠게 1 token ≈ 4 characters라고 놓으면:

20,000,000 tokens
≈ 80,000,000 characters

GPT-5.6이 한 이미지에서 볼 수 있는 최대 patch 면적은 대략:

30,000 patches × 32 × 32
≈ 30.7 million pixels

따라서 문자 하나당:

30.7M pixels / 80M chars
≈ 0.38 pixels / character

밖에 없습니다.

한 글자가 1픽셀도 안 됩니다.

실제로 문자 하나를 간신히 구분하려 해도 최소 수십 픽셀 정도는 필요하므로 한 장에는 물리적으로 안 들어갑니다. OpenAI도 작은 텍스트는 확대하라고 공식적으로 명시합니다. 

Claude도 같은 문제가 있습니다. 현재 고해상도 tier조차 한 이미지당 최대 2,576px long edge와 4,784 visual tokens를 사용하고, 이를 넘는 이미지는 축소됩니다.

그럼 여러 장으로 쪼개면?

여기서부터는 가능성이 생깁니다.

가령:

20M text tokens

↓ 10× optical compression

2M visual tokens

DeepSeek-OCR은 자사 전용 optical compressor에서 10× 이하의 text/vision ratio일 때 약 97% OCR precision을 보고했습니다. 

그런데 GPT-5.6 Sol context는:

1.05M total tokens

입니다.

그러니 10× 압축으로도:

20M
 └─10×→ 2M visual
           ↑
       1.05M보다 큼

이라 한 번에 안 들어갑니다.

20×로 밀면:

20M
 └─20×→ 1M visual tokens

이라 숫자상으로는 거의 들어갈 것처럼 보입니다.

하지만 DeepSeek-OCR 자체에서도 **20×에서 OCR 정확도가 약 60%**로 떨어집니다. 

더 나쁜 점은 후속 연구에서 의미가 불규칙한 텍스트에서는 고압축 OCR 성능이 훨씬 심하게 떨어지고, 언어 모델이 안 보이는 글자를 문맥으로 추측하는 비율이 커진다는 결과가 나왔다는 겁니다. 

코드라면 치명적입니다.

실제:
cache_key_7F9A

모델이 이미지에서:
cache_key_7F94

가 될 수 있습니다.
