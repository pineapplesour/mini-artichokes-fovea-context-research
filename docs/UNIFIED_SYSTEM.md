# 통합 법률 엔진 — 하나의 원리로 세무·판결예측·법률문제

## 왜 통합인가

각 능력을 따로 만들면 벤치마크가 4개 생길 뿐이다. 실제로 필요한 것은
**하나의 메커니즘**이 세무 결과 예측, 판결 결과 예측, 법률 문제 해결을
모두 수행하고, 각 도메인의 성적 차이를 같은 언어로 설명하는 것이다.

## 원리

    분해 → 독립 시도/검증 → 원장 종결 → 결정적 합성 + 완결 게이트

이 원리는 이번 연구에서 도메인마다 독립적으로 재발견됐다.

| 벤치 | 단일 호출이 무너진 방식 | 같은 처방 |
|---|---|---|
| 시험 1,309문항 | 파일 전체를 한 번에 풀면 항목별 추론 붕괴 (48.8%) | 문항 분해 + 독립 드래프트 + 판정자 (85.0%) |
| 법률 E2E 10문제 | 검색을 하지 않거나, 검색해도 읽지 않음 | 문제당 격리 실행 + 읽기 게이트 + 인용 게이트 (8/10) |
| 중화 재작성 | whole-file 재작성이 복사로 퇴화 (87/120 탈락) | per-case 격리 + verbatim-copy 게이트 (112/120) |
| 판결 결과예측 | 세 가지 독립 프레이밍이 84% 합의하고도 75%, 분열 구간은 정확히 우연 | 최종 합성을 모델에서 **코드로** 이관 |

마지막 줄이 이번 단계의 핵심이다. 투표는 상관된 오류를 고치지 못한다.
`tools/universal_engine.py`는 모델에게 **결론을 묻지 않는다**. 모델은 명제
단위 판정만 하고, 결론은 파이썬이 결정적으로 합성한다.

## 엔진 구조 (`tools/universal_engine.py`)

```
stage 1 DECOMPOSE   사건 → 요건사실/항변 명제 목록 (원자성 게이트: 110자 이하,
                    접속 2개 이상 금지 → 복합명제는 파싱 단계에서 탈락)
stage 2 VERIFY      명제 1개당 격리된 호출 1회. 다른 판정을 절대 보지 못함
                    → 오류가 연쇄되지 않음. 출력은 판정/확신도/근거 3줄 고정
stage 3 LEDGER      모든 판정이 근거 인용과 함께 원장에 기록 (감사 가능)
stage 4 SYNTHESIZE  코드가 부호 질량으로 합성:
                    요건 충족 +conf, 불충족 −conf, 불명 0, 항변 충족은 감산.
                    부호가 결론, 마진이 확신도. 무승부만 에스컬레이션
stage 5 GATE        형식·완결 게이트 실패 시 그 조각만 재실행
```

도메인은 프로파일로만 갈린다: 무엇이 명제인가, 합성 규칙, 게이트.
백엔드는 OpenRouter(계량 API)와 codex(구독 Luna, bwrap 격리) 둘 다 지원 —
같은 엔진 로직으로 저비용 대규모 재현이 가능하다.

## 세무가 어려운 이유 (측정된 사실)

세무 벤치는 청구취지를 **의도적으로 제거**했다. 조세 판결문의 청구취지는
"주문과 같다"로 적히는 일이 잦고(즉 주문 전문 복사), 그 존재 자체가 전부인용과
상관된다. 그래서 처분 경위 + 양측 주장만 남겼다. 그 결과 55.0% — 민사(72.5%)
보다 17%p 낮다. 조세 사건은 사실관계보다 **법령 해석과 실질과세 판단**이
결론을 가르기 때문에, 유사 사건 검색 증강이 민사보다 더 중요할 것으로 보인다
(검증 진행 중).

확신도 운영점은 여전히 작동한다: conf≥0.8 → 72.2%(커버 30%), conf≥0.9 →
5/5=100%. 정확도가 낮은 도메인에서도 **어디를 사람이 봐야 하는지**는 안다.

python3 tools/run_unified_suite.py --manifest suites/unified.json --out runs/unified-$(date +%Y%m%d)

# 엔진 단독 (무료 백엔드)

    --backend codex --codex-home ~/.codex-7 --profile outcome_civil
